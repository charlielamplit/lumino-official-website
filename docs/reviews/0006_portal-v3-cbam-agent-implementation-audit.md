# Lumino Portal v3 · CBAM 页面与服务 Agent 实现审计

审计日期：2026-11-12
审计对象：当前 `dev` 工作树（`194f254` 之上的未提交改动）
设计基准：`Demo/Lumino Portal设计框架优化/Lumino Portal 原型 v3.dc.html`
范围：CBAM 当前工作、全年流程、季度数据、产品与工厂、计算与成本、报告与交付，以及服务级 Agent Runtime。

## 1. 结论

当前实现已经完成 v3 的主要页面结构、视觉层级和 10 个 Agent 阶段的前端演示，但尚不能被视为完整的业务实现。

最关键的差距不是视觉，而是状态真实性：Agent 可以在界面上显示“已提交、已发送、已共享、已锁定、已写入审计记录”，但除年度范围的一小部分本地状态外，并未驱动现有工作流、资产、权限、审批、交付或计算引擎。当前更准确的定位是：**可交互的高保真原型，而不是已闭环的 CBAM Agent。**

发布判断：**不建议按正式能力合并发布；可以作为明确标注的演示版本继续内部评审。**

## 2. 验证结果

- JavaScript 语法检查：通过。
- 全量现有测试：73/73 通过。
- `git diff --check`：通过。
- `dev` 与 `origin/dev`：0 ahead / 0 behind；但审计对象包含 8 个未提交文件，其中 2 个 Agent 文件尚未跟踪。
- 浏览器自动化：本轮本地预览服务可启动，但浏览器控制宿主不可用，因此没有把 320/390/768/1440 的实际截图或控制台结果计入“已验证”。
- 测试覆盖缺口：现有 73 项测试没有引用 `agent-runtime.js`、`agent-catalog.js` 或 p01–p10，不能覆盖本次新增 Agent 行为。

## 4. 评分

评分标准：0 = 不可用，1 = 重大缺陷，2 = 基础可用但明显不完整，3 = 良好且有少量缺口，4 = 可发布质量。

| 维度 | 分数 | 说明 |
|---|---:|---|
| Accessibility | 2/4 | 有语义按钮、Escape、全局 focus-visible；但 Agent 模态框无初始焦点、焦点圈定与返回，tab/radio 缺 `aria-selected` / `aria-checked` |
| Performance | 3/4 | 纯静态实现、运行成本低；但新增约 800 行 Agent JS 和 1200 行 CSS 全量加载，Runtime 每次操作整体重绘 |
| Theming | 2/4 | 大体沿用 Portal 品牌；Agent CSS 仍大量硬编码颜色和 10–11px 标签，未完全使用设计令牌 |
| Responsive | 1/4 | 布局不会直接溢出是正向项；但移动/平板隐藏了任务选择与产物检查的核心操作入口 |
| Anti-patterns | 1/4 | 关键业务动作以“已完成”呈现但没有真实执行；模式、附件、工具、来源和日志多为装饰性或模拟性 |
| **综合** | **1.8/4（45/100）** | **适合演示，不满足正式业务发布条件** |

## 5. 问题清单

### P0

本轮未定为 P0。原因是新增 Agent 尚未接入正式后端，也没有真实写入生产数据。若把当前按钮直接连接生产 API，而不先修复下述权限与状态问题，权限绕过将升级为 P0。

### P1-1 · Agent“完成”不等于业务完成

`finishPlaybook()` 主要把 `rtDone[pb.id]` 设为真，并把静态变更集显示为“已提交”。除 p03 写入 `prodDec` 外，p01/p02/p04–p10 不会创建项目、发布监测计划、发送邀请、确认数据、调用计算、提交审批、共享数据包、锁定报告或创建下一年度草稿。

影响：用户会看到与真实业务状态矛盾的成功提示；刷新后又全部消失。

建议：为每个 playbook 定义真实 command contract、前置条件、权限、幂等键、成功回执与失败恢复；只有收到领域引擎确认后才能标记完成。

### P1-2 · 登录角色和 Agent 确认权限脱节

Agent 对所有 customer 角色开放；确认逻辑只看 `agentAs` 是 `client` 还是 `expert`，不检查 `state.role` 或现有权限模块。客户贡献者可以以“客户”视角执行协调人确认；任何客户都能切换“专家”演示视角，并依次代表王晨、李娜完成制备和独立复核。

影响：职责分离在页面层被破坏；未来一旦接入真实写入会形成越权风险。

建议：移除运行时身份切换作为正式交互；按登录身份、任务受让人和权限 capability 判断按钮；制备与复核必须是不同主体和不同审计事件。

### P1-3 · 没有阶段门禁，p01–p10 可任意执行和重跑

当前所有 playbook 均可随时开始，未校验年度、季度、上一步完成状态、审批状态或数据完整性。已完成任务也能重新开始，可能重复“发送邀请”“共享”“锁定”等动作。

影响：流程顺序、幂等性和审计一致性无法保证。

建议：把设计中的 gate 转成可执行前置条件；对外部动作增加幂等键和再次执行确认；状态由领域对象推导，不能只用 `rtDone`。

### P1-4 · 通用 Agent 能力没有接入

自由问答只对 `AG_REPLY` 中的预置文本做精确匹配，未知问题返回“原型中暂无专属回复”；代码中没有 API 请求、模型调用、检索、文件读取或上下文工具调用。“问答/执行任务/仅起草”三种模式共用同一条本地回复路径。

影响：不符合“不能限定不回答范围，至少给反馈和结果”的既定产品要求，也无法利用当前页面真实数据回答。

建议：接入受控 Agent API；预置答案作为确定性快速路径，其余问题进入模型路径；工具结果、来源和模型失败需分别表达，不得伪装成已读取。

### P1-5 · 平板和手机隐藏核心导航

小于 1200px 时左侧 playbook 列表消失，小于 1000px 时右侧产物/变更集也消失。v3 原型设计了小屏任务选择器和面板切换，当前实现没有对应替代入口；只有 dock 模式出现一个有限的页签交换按钮。

影响：手机用户无法选择大多数阶段，也无法在提交前检查变更集与依据；p04、p09 尤其难以进入。

建议：补齐 v3 的阶段选择器；在小屏提供“对话 / 产物 / 变更集 / 依据 / 日志”明确切换，并在 390px 进行完整键盘与触控回归。

### P1-6 · Agent 状态与审计日志不持久化

`persistPortalState()` 明确没有保存 Agent 会话、步骤、回答、完成状态或日志。界面却使用“已写入审计记录”“已提交”等确定性措辞。

影响：刷新、重新登录或换设备后无法恢复；也不存在可追溯审计证据。

建议：会话与任务状态存储到服务端；审计事件只追加并包含 actor、role、object、version、reason、timestamp、request id；本地草稿应明确标注“仅本机未提交”。

### P2-1 · 监测计划与创建项目页面没有按 v3 落地

- p02 声称存在 5 步向导，但当前页面没有该向导。
- p04 设计中的客户审阅、专家制备、独立复核工作区没有实现；全年流程的“查看监测计划”仍只显示占位 toast。
- `deliverables` 的页面 CTA 被硬编码为 p08，目录映射中的 p04 不会生效；p09 也没有页面级入口。

建议：先补齐两个高价值页面，再决定是否保留 Agent 内嵌产物表。

### P2-2 · 计算、数据、交付页面与 Agent 是平行状态机

页面已有 workflow/asset/task 引擎和明确的演示动作，但新增 Runtime 不读取这些对象，也不更新它们。p06 完成不会把能源/产量任务变为完成；p07 不调用计算引擎；p08 不调用正式共享；p09 不锁定报告。

建议：Agent 不维护第二套 `rtDone` 业务真相；应调用现有领域服务并从领域对象回读状态。

### P2-3 · 模态框键盘和 ARIA 不完整

打开 Agent 后没有把焦点移入对话框，没有 Tab focus trap，也没有关闭后的焦点返回。tab 按钮缺 `aria-selected` 和 panel 关联，radio 按钮缺 `aria-checked`。动态执行完成也没有稳定的 live region。

建议：复用现有 drawer 的焦点圈定模式，并补齐 WAI-ARIA dialog/tabs/radiogroup 行为。

### P2-4 · “依据可追溯”只是文本展示

来源页签展示文件名或对象名，但不是可打开、可定位版本和页码的链接；同时文案声称“每个结论都链接到这些来源”。

建议：来源必须绑定 asset/evidence id、版本、访问控制与定位信息；无权限时显示受限元数据，不可退化为虚构可追溯性。

### P2-5 · 新 Runtime 没有专项测试

现有 73 项回归全部通过，但没有覆盖新增两个 Agent 文件。缺少：角色矩阵、阶段门禁、重入/幂等、刷新恢复、移动端导航、键盘焦点、API 失败、跨页面状态同步和正式动作禁止误报。

建议：新增目录契约测试、Runtime 状态机测试、权限测试和至少一组 390/768/1440 浏览器用例。

### P2-6 · 等待体验与既定要求不一致

自由问答固定等待 480ms；v3 原型为 1100ms，此前产品要求是预置回答也应有 1–4 秒波动。自动步骤也只有固定 520/900ms。

建议：预置回复采用可取消的 1–4 秒区间，并展示真实阶段；真实 API 以实际延迟为准，不额外伪造已完成工具调用。

### P3

- Agent 样式中存在大量硬编码色值，后续主题和品牌令牌调整成本高。
- 多处 10–11px 标签在中文与高 DPI 场景可读性偏弱。
- 2026、Q3、周岚、王晨、李娜、NordWerk 等上下文硬编码在目录中，无法安全复用于其他企业或年度。
- 两个 Agent 脚本和全部样式对所有 Portal 角色全量加载；正式化后应按客户/服务上下文延迟加载。
- 顶栏按钮只有 `title`，建议增加更明确的可访问名称与当前任务提示。

## 6. 正向项

- CBAM 六个主要页面的信息架构比旧版更集中，全年流程、季度循环和交付状态的层级明显改善。
- 计算页对“演示数据、不构成报价或合规结论”有清晰提示，页面自身的风险表达优于 Agent Runtime。
- Runtime 将输入、产物、人工确认、变更集、依据和日志拆开，方向正确。
- 关键文本经过 HTML 转义；现有全局 focus-visible 和 reduced-motion 规则可复用。
- 现有 workflow、asset、AgentTask 和 permission 基础模块已经存在，不需要另建第三套领域模型。

## 7. 建议修复顺序

1. **先修真实性与权限**：把成功状态改为演示/草稿，或接入真实 command；绑定登录身份与 capability，禁止模拟身份执行正式确认。
2. **统一状态源**：Agent 调用现有 workflow、asset、task、calculation、delivery 对象，不维护平行业务状态。
3. **补阶段门禁与持久化**：前置条件、幂等、失败恢复、服务端会话与只追加审计事件。
4. **补通用 Agent API**：预置路径 + 模型路径 + 工具结果 + 可核验来源；附件和三种模式必须真实工作。
5. **补缺失页面与小屏交互**：项目向导、监测计划工作区、移动端任务选择和产物面板。
6. **最后做可访问性、主题与性能收口**：focus trap、ARIA、令牌化、小字号、按需加载和浏览器矩阵。

## 8. 完成定义

满足以下条件后，才建议把 v3 标为“已实现”：

- p01–p10 每个最终动作都有真实领域 command、权限校验、幂等与失败态。
- 页面和 Agent 从同一业务对象读取状态；刷新与换设备可恢复。
- 制备、复核、客户确认和外部共享保持职责分离。
- 未知问题能进入模型路径；模型失败时给出明确但可用的降级结果。
- 文件、来源、变更集和审计日志可追溯到真实资产与版本。
- 390/768/1440px 完成任务选择、问答、确认、产物检查和关闭恢复；键盘路径通过。
- 新 Runtime 专项测试通过，且不再以静态 `rtDone` 代替正式业务完成。
