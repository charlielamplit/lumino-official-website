# Lumino 官网全站用户体验与发布准备审计

> 文档编号：0001  
> 审计日期：2026-10-29  
> 审计对象：Lumino 官网、服务页、平台页、行业解决方案、案例、工具、知识库、关于与联系页面  
> 审计基线：本地 `main` 分支及当前未提交设计草稿  
> 文档状态：持续更新；已完成 0.2.3 演示环境安全收口

## 1. 审计目的

本次审计从潜在客户的使用视角出发，判断网站是否能够完成以下任务：

1. 让第一次访问者快速理解 Lumino 是什么；
2. 让客户判断自己需要哪项服务；
3. 让已有明确需求的客户理解服务过程、输入和交付物；
4. 通过案例、方法、公司和平台信息建立信任；
5. 让客户顺利提交咨询并进入后续服务；
6. 确保桌面端、移动端和正式部署环境具备基本发布质量。

本次审计不评价服务由多少系统、Agent 或人工完成。对客户而言，六项服务均是 Lumino 可以承接并完成的服务。

## 2. 对外表达原则

### 2.1 服务能力与系统成熟度分离

对外官网表达的是服务能力，不表达内部交付方式差异：

- 六项服务均按可承接、可交付进行说明；
- 不公开“试点、规划中、手动完成、系统完成”等内部标签；
- 不向客户解释具体环节由人工还是系统完成；
- 重点说明客户问题、所需资料、Lumino 的工作过程和最终交付物。

内部可以记录系统化成熟度，但不得被官网直接读取。建议将内容模型拆为两层。

#### 公共服务目录

- `serviceId`
- 服务名称
- 核心承诺
- 适用对象
- 触发场景
- 客户输入
- 服务过程
- 交付物
- 法规、标准和来源
- 能力边界
- 主要操作
- 最后内容审查日期

#### 内部交付治理

- 系统覆盖程度
- 自动化覆盖率
- 人工操作节点
- 生产环境可用性
- 所需专家角色
- 后台依赖
- 风险与补偿流程

核心原则：

> 服务能力真实性，不等于系统自动化成熟度。官网承诺的是 Lumino 能否完成交付，而不是具体由多少软件、Agent 或人工完成。

### 2.2 真实性要求

官网可以完整表达服务能力，但下列内容必须可以被内部证据支持：

- 客户案例和效果数字；
- 项目周期与响应时间；
- 公司资质、团队履历和合作关系；
- 软件安全、权限隔离、版本锁定等平台能力；
- 法规、标准、参数和适用日期；
- 计算结果、报告和交付物样张。

## 3. 总体结论

当前网站已经具备较好的视觉基础。首页首屏、Header 和行业解决方案页具有比较明确的 Lumino 品牌感，整体风格清晰、专业、克制。

但当前成果仍属于高保真官网草稿，不建议直接作为正式官网发布。主要阻碍已经不是视觉，而是以下五项：

1. 信任证据和真实内容不足；
2. 咨询转化链路没有接入真实接收系统；
3. 六项服务页内容过于同质和简略；
4. 知识库、指南、案例仍存在失效入口和占位内容；
5. 本地图片资产、元数据和自动化检查尚未达到发布要求。

## 4. 用户旅程审计

### 4.1 第一次访问者

用户能够快速看到 Lumino 涵盖 CBAM、PCF、ESG、碳盘查、碳资产与绿证及出口合规，也能理解企业数据可被多项服务复用。

尚未解决的问题：

- 我现在应该优先做哪项服务；
- 我需要准备什么资料；
- 项目如何启动、多久完成；
- 最终可以拿到什么；
- 为什么应该信任 Lumino。

建议增加一个不涉及内部系统状态的需求判断入口，例如按“客户要求、出口市场、产品、截止时间”给出建议服务组合。

### 4.2 已有明确需求的项目负责人

进入服务页后，用户可以看到适用对象、标准、四步过程和三项交付物，但六个页面结构与标题过于一致，无法体现专业差异。

用户还需要看到：

- 典型触发场景；
- 需要提供的资料；
- 参与部门与职责；
- 项目启动方式；
- 关键判断和风险；
- 交付物示例；
- 咨询时应提供的信息。

### 4.3 查资料和验证专业能力的用户

当前知识路径基本不可用：

- 知识库六项内容中五项使用 `href="#"`；
- 唯一可访问的 CBAM 指南仍为未完成模板；
- 页面会直接显示 `{{ a.title }}` 等模板变量；
- `support.js` 返回 404；
- 指南和文章在移动端存在横向溢出。

这会直接削弱用户对专业能力的判断。

### 4.4 准备咨询和采购的用户

联系页结构清楚，但尚未形成真实转化闭环：

- 邮箱为 `contact@lumino.example`；
- 表单只在浏览器本地模拟成功；
- 页面承诺一个工作日回复，但数据不会发送；
- 没有隐私政策、数据用途和保存期限说明。

## 5. 页面级审计

### 5.1 首页

#### 做得好的地方

- 首屏视觉完成度较高；
- Header 和主要操作清晰；
- 六项服务与企业数据底座可以同时被理解；
- 1440px 首屏控制合理；
- 390px 下标题和两个主要操作均可见，页面无整体横向溢出。

#### 需要调整

- “应对全球绿色要求，一个平台就够”偏绝对，容易把服务能力误解为全部由软件自动完成；
- 案例仍包含 `[X]` 占位值；
- 服务、行业、案例、工具和知识内容同时展开，后半段信息密度偏高；
- 缺少“我应该选择什么服务”的判断入口；
- 案例数据未准备好时应隐藏 KPI，而不是公开占位数字。

建议首页只承担以下任务：

1. 说明 Lumino 的核心定位；
2. 说明客户能获得的三项关键价值；
3. 展示六项服务；
4. 提供行业入口；
5. 展示真实证据或交付成果；
6. 引导咨询。

### 5.2 六项服务页

当前六页使用同一个泛化标题“六项核心服务，流程清晰、专家交付”，具体服务名称降为二级标题。页面缺少独立 `title`、description 和服务级主问题。

建议每项服务采用统一但不机械的内容契约：

1. 这项服务解决什么问题；
2. 何时应该启动；
3. 适用于谁；
4. 客户要准备什么；
5. Lumino 如何开展；
6. 客户会收到什么；
7. 典型交付样张；
8. 常见边界与注意事项；
9. 咨询时应提供哪些信息。

各服务必须体现业务差异：

| 服务 | 需要突出表达的内容 |
|---|---|
| CBAM | CN 编码、工厂范围、前体、能源、实际值与默认值、进口商交付、核查支持 |
| PCF | 功能单位、系统边界、模板导出与回传、生命周期清单、因子、分配、热点、不确定性、报告 |
| ESG | 报告目标、适用框架、议题、指标、责任人、证据、编制和审阅 |
| 碳盘查 | 组织边界、基准年、范围一二三、排放源、年度变化和盘查报告 |
| 碳资产与绿证 | 用电需求、目标比例、凭证、匹配、注销和声明材料 |
| 出口合规 | 目标市场、产品要求、法规矩阵、测试和证书差距、文件交付 |

### 5.3 平台介绍页

平台页已经形成企业数据底座、服务频道、任务、资料、交付和权限的基本叙事。

正式发布前应检查两类内容：

1. 移除“稍后替换”等制作过程说明；
2. 对企业租户隔离、原始资料不可覆盖、对象授权、版本锁定、全程留痕等软件能力逐项核验。

服务可以通过人工与系统共同交付，不代表所有软件能力都已经在生产环境中实现。平台页应重点回答：

> 客户如何在 Lumino 中查看项目、提交资料、确认事实、跟踪进度和接收交付。

### 5.4 行业解决方案

这是当前完成度最高的分页面之一：

- 行业差异明确；
- 图片与正文配合较好；
- 页面不是简单卡片墙；
- 用户能够理解行业问题与建议优先事项。

建议补充：

- 为化工、电子电器建立稳定独立路由；
- 不只依赖 `?industry=` 查询参数；
- 每个行业提供“优先准备资料”清单；
- 增加行业相关服务、案例和知识文章的交叉链接；
- 为法规事实标注适用日期和来源。

### 5.5 项目案例

当前案例页面不应直接发布，原因是仍存在 `[X]` 占位数字。

处理方式按优先顺序为：

1. 补充经过内部确认的匿名真实数据；
2. 如果数字不能公开，则使用定性案例，不显示 KPI；
3. 如果案例尚未完成，则暂时隐藏案例板块和入口。

案例重点应是问题、工作过程、交付物和客户获得的业务结果，不需要增加“经客户同意后公开”等解释性说明。

### 5.6 工具和 CBAM 计算器

工具中心结构清楚，但浮动“测算”菜单中的 PCF、企业排放和绿电需求实际跳转到联系页，并不是即时在线工具。

建议将文案改为：

- 申请产品碳足迹初步估算；
- 申请企业排放初步估算；
- 申请绿电需求测算。

CBAM 计算器当前存在：

- 与主站视觉体系不一致；
- 页面没有 `h1`；
- 390px 下存在输入框横向溢出；
- favicon 路径返回 404；
- 初始状态右侧存在大面积空白；
- 项目入口仍指向 `/portal/`；
- 部分辅助文字过小、对比度不足。

计算器应纳入主站 Header、字体、按钮、间距和移动端系统，并在结果附近显示参数日期、数据来源、适用范围和计算限制。

### 5.7 知识库与指南

这是当前内容缺口最大的区域，建议整体迁移到新版站点壳层。

每篇知识内容至少包含：

- 发布日期；
- 最后复核日期；
- 作者或专业复核人；
- 适用地区和法规时间点；
- 来源链接；
- 本文解决的问题；
- 相关服务；
- 下一步操作；
- 变更记录。

发布前必须清零：

- `href="#"`；
- 未解析模板变量；
- 缺失脚本；
- 失效首页锚点；
- 移动端横向溢出。

### 5.8 关于我们

公司主体、定位和国际资源已有基础，但团队区域仍使用成员照片和资料待补说明。

建议：

- 有真实姓名、照片和履历后再展示团队；
- 资料未齐时使用“能力团队结构”，不显示人物占位；
- 补充真实办公地址、企业联系方式和必要主体信息；
- 国际合作、项目经验和资质只展示可验证内容；
- 关于页的服务范围应与六项服务保持一致。

### 5.9 联系我们

联系页布局、服务多选和敏感资料提示是合理的。

正式上线前必须完成：

- 替换真实邮箱；
- 接入真实线索接收接口；
- 保留离线、失败、重复提交和成功状态；
- 增加隐私政策和数据用途说明；
- 明确表单数据的保存范围和联系方式；
- 确保“一个工作日回复”具备真实运营能力。

### 5.10 Header 与 Footer

Header 视觉清楚，但七个一级入口略多。建议收敛为：

- 服务；
- 解决方案；
- 平台；
- 资源；
- 关于；
- 联系。

工具与知识库可进入“资源”。

Footer 建议补充：

- 隐私政策；
- 服务条款；
- 数据处理说明；
- 企业主体信息；
- 备案信息（如适用）。

公开 Footer 不应出现“原型”“示例数据”等制作过程说明。

## 6. 视觉、响应式与可访问性

### 6.1 首屏

- 1440px 下首页价值主张、主要操作和平台概览均能在首屏被理解；
- 390px 下标题、说明和两个操作可见，但平台概览卡片继续延伸到下一屏；
- 如果要求整个概览卡片也必须位于单屏内，应将其移至首屏之后；
- 当前新版页面整体没有横向溢出。

### 6.2 移动端问题

- CBAM 指南和指南文章存在横向溢出；
- 计算器输入控件在 390px 下溢出；
- 服务页的横向服务导航需要更明确的可滚动提示；
- 浮动测算入口应避免遮挡底部主要操作。

### 6.3 可访问性问题

- 计算器缺少 `h1`；
- 旧内容页的导航状态和模板内容不完整；
- 计算器存在低对比度辅助文字和过小字体；
- 内容图片如果承担信息作用，应使用描述性 `alt`，不能全部使用空文本；
- 动态表单和计算结果需要结构化状态提示。

## 7. 性能与资产

当前 `apps/site/site/assets/` 约 26MB，多数单图为 1.9–2.8MB PNG。

发布前建议：

1. 生成 AVIF 和 WebP；
2. 保留必要的 PNG 原图作为源文件或设计归档；
3. 为首页和行业图生成多尺寸版本；
4. 使用 `srcset` 和 `sizes`；
5. 首屏只预加载真正可见的图片；
6. 非首屏图片继续延迟加载；
7. 建立单图和单页资源预算；
8. 将正式引用资产纳入 Git 或明确的外部资产管线。

当前图片目录尚未被 Git 跟踪。页面引用这些文件时，如果只提交 HTML/CSS 而没有提交资产，部署环境将出现断图。

## 8. SEO 与内容发现

当前缺口包括：

- 六项服务页使用相同标题“服务 · Lumino”；
- 服务页缺少独立 meta description；
- 缺少完整 canonical；
- 缺少 Open Graph 与 Twitter Card；
- 缺少结构化数据；
- 缺少 sitemap 和 robots；
- 缺少 `hreflang`；
- 行业详情主要依赖查询参数；
- 英文版并未覆盖旧指南和计算器。

建议增加：

- `Organization`、`Service`、`Article`、`FAQPage` 等 JSON-LD；
- 每页唯一标题和描述；
- 中英文 canonical 与 hreflang；
- 可抓取的六项服务和六个行业详情路由；
- 知识文章更新时间和作者信息；
- 自动生成 sitemap。

## 9. 内容源与测试问题

当前同时存在：

- `apps/site/site/service-registry.js`
- `apps/site/site/services-catalog.js`

现有契约测试验证前者，但公开服务页读取后者。因此即使测试通过，服务页仍可能发生内容漂移。

建议：

1. 建立唯一公共服务内容源；
2. 将内部系统化成熟度移入非公开配置；
3. 官网只读取公共服务内容；
4. 测试公共页面实际渲染结果，而不仅验证未被使用的注册表；
5. 增加占位符、死链接、重复标题、缺失 meta 和未跟踪资产检查。

当前 13 项 Node 测试全部通过，但这些测试主要覆盖数据资产、权限和服务契约，不能证明公开网站可以发布。

## 10. 优先级清单

### P0：正式发布前必须清零

1. 接通真实咨询提交并替换真实邮箱；
2. 清除 `[X]`、模板变量和失效内容；
3. 修复知识库、指南和文章；
4. 修复计算器 Portal 链接、favicon 与移动端溢出；
5. 处理未跟踪图片并完成资源优化；
6. 移除公开页面中的制作过程说明；
7. 核验平台安全、权限和版本能力声明；
8. 增加隐私与数据处理说明。

### P1：核心内容完善

1. 重写六项服务页；
2. 建立客户需求判断入口；
3. 增加真实交付样张；

### 16.10 Cookie 与类似技术的同意门禁

#### 当前结论

截至 2026-10-30 的代码扫描，没有发现 `document.cookie`、Google Analytics、Google Tag Manager、广告像素、会话回放或其他跨站追踪工具。当前可见的浏览器端存储主要为：

- 官网语言偏好：`localStorage`；
- 联系表单重复提交标记：`sessionStorage`；
- Portal 角色、引导状态、工作流与本地演示数据：`localStorage` / `sessionStorage`。

这些技术仍属于应向用户透明说明的终端存储或访问技术，但在仅用于用户明确请求的语言、会话、安全和核心功能，且不用于分析、画像、营销或跨站跟踪时，当前不建议显示“接受全部 Cookie”弹窗。应在隐私页或独立 Cookie / 本地存储说明中列出真实名称、用途、保存期限、数据范围和清除方式。

隐私页及独立《Cookie 与本地存储说明》现已按代码与部署事实区分 Cookie、`localStorage` 和 `sessionStorage`，后续新增或改变终端存储时必须同步更新清单。

#### 需要事前同意的典型触发条件

出现下列任一情况时，应重新进行法律与技术评估；面向欧盟用户时，原则上应在写入或启动前取得可撤回的明确同意：

1. 接入 Google Analytics、Adobe Analytics、Matomo 非必要配置或其他访问行为统计；
2. 接入广告像素、再营销、跨站识别、受众画像或个性化推荐；
3. 接入 Hotjar、Microsoft Clarity 等会话回放、热图、鼠标轨迹或表单行为分析；
4. 页面加载 YouTube、地图、社交分享、在线客服等会在用户设备写入标识符或向第三方发送访问数据的嵌入组件；
5. 将设备标识、IP、访问记录与 CRM、广告平台或其他数据源结合；
6. 使用非核心 A/B 测试、营销归因或个性化内容存储；
7. 原先仅用于必要功能的标识符被改用于分析、营销、画像或其他新目的；
8. 第三方服务商、处理目的、保存期限或跨境路径发生实质变化。

中国法下不以“是否叫 Cookie”为唯一判断，而应看是否处理个人信息、处理目的、必要性、告知和合法性基础。涉及敏感个人信息、向其他处理者提供、公开或特定跨境处理时，还应单独判断单独同意及其他法定义务。

#### 同意组件验收要求

如果触发同意机制，至少应满足：

- 首次访问时只启用严格必要类别，分析、偏好扩展和营销默认关闭；
- “仅接受必要项”与“接受全部”同层级、同等易见，不使用诱导性设计；
- 用户可以按目的分类选择，而不是一揽子同意；
- 同意前不加载非必要第三方脚本、不写入非必要标识符；
- 记录同意版本、时间、类别和政策版本，但避免记录不必要的身份信息；
- 页脚持续提供“Cookie 设置”，撤回同意与接受同样容易；
- 撤回后停止后续处理并删除可删除的非必要标识符；
- 隐私页、Cookie 清单、实际网络请求和浏览器存储保持一致；
- 中英文文本同步更新，并记录最后审查日期。

#### 复审触发点

以下变更不得仅按普通前端功能发布，必须同时更新隐私审查：新增第三方 `<script>` / `<iframe>`、新增 `document.cookie`、新增本地存储键、接入分析或营销 SDK、修改表单字段、修改线索流向、启用新的外部托管或跨境服务商。

参考依据：欧盟官方在线隐私与 Cookie 指引区分严格必要技术与需要事前同意的分析、市场研究和行为广告技术；中国《个人信息保护法》以处理行为、目的、必要性、告知和合法性基础为核心，而不是以技术名称决定是否需要同意。
